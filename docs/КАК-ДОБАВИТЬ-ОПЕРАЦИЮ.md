# Как добавить операцию в базу знаний

Регламент для тех, кто наполняет базу знаний «Скаут Хаус». Описывает, какие
файлы менять и в каком порядке, чтобы новая операция появилась в разделах,
в поиске и в контроле ознакомления.

---

## 1. Из чего состоит операция

Одна операция — это шесть независимых точек в репозитории. Пропущенная точка
не даёт ошибки в консоли: страница просто не появится в списке, не найдётся
поиском или потеряет фото.

| # | Что | Где |
|---|-----|-----|
| 1 | Техкарта (PDF) | `public/assets/docs/` |
| 2 | Фотографии шагов | `public/assets/images/operations/X.Y.Z/` |
| 3 | Страница операции | `public/pages/operations/X.Y.Z.html` |
| 4 | Запись в реестре | `public/js/kb.js` → `KB_OPERATIONS` |
| 5 | Ссылка в списке подраздела | `public/pages/<раздел>.html` |
| 6 | Поисковый индекс | `public/js/search-index.json` (генерируется) |

Раздел определяется первой цифрой номера: `1.x` → Заготовка, `2.x` → Сборка
панелей, `3.x` → Сборка модуля, `4.x` → Опции, `5.x` → Монтаж, `6.x` → Сервис,
`7.x` → Стандарты.

---

## 2. Два сценария

**A. Есть только техкарта (текущая практика).** Создаётся страница-заглушка:
блоки «Производимые операции», «Контрольные параметры», «Инструмент»,
«Материалы» и «Фотоальбом» закомментированы, вместо них стоит заголовок
`СТРАНИЦА НА СТАДИИ ЗАПОЛНЕНИЯ`. Статус в реестре — `draft` или `ready`
(см. § 5), поиск находит операцию только при `ready`.

**B. Полное наполнение.** Заполняются все шесть блоков: документация,
пошаговые операции с фото, контрольные параметры, инструмент, расходные
материалы, ссылка на фотоальбом.

Порядок действий в обоих случаях одинаковый, отличается только объём текста.

---

## 3. Пошагово

### Шаг 1. Техкарта PDF

Положить файл в `public/assets/docs/`. Имя — `<id операции>_<тема>.pdf`,
например `3.4.3_монтаж РК внутри панели стены.pdf`: префикс до первого `_`
равен номеру операции, на странице которой документ используется.

Если на одну техкарту ссылаются несколько операций, префикс берётся по
**самой ранней** из них (наименьший номер) — так документ имеет одно
стабильное имя, а остальные операции ссылаются на него. Пример: альбом
`2.1.1_standard assembly components.pdf` используется в 2.1.1, 2.2.1, 2.3.1,
2.3.2 и 2.4.2.

Кириллица и пробелы в имени допускаются (в `href` они кодируются браузером
автоматически). Тема после `_` — по-русски или по-английски, как удобнее;
важна только уникальность полного имени.

### Шаг 2. Фотографии шагов

Папка `public/assets/images/operations/X.Y.Z/`, имена `step1.jpg`, `step2.jpg`
(или `step4-shkant1.jpg`, если у шага несколько кадров). Ссылка в странице —
относительная:

```html
<img src="../../assets/images/operations/3.1.5/step1-1.jpg" alt="Монтаж ленты ГОСТ-1">
```

> ⚠️ Если файла нет, сайт **молча скроет** весь блок с фото
> (`hiding-empty-blocks.js`). Ошибки в консоли не будет — шаг останется без
> иллюстрации, и заметить это можно только глазами. Проверяйте через
> `npm run audit`.

### Шаг 3. Страница операции

Скопировать `public/pages/operations/template.html` в `X.Y.Z.html` и заменить:

1. `<title>` — `Название операции | Скаут Хаус`;
2. хлебные крошки — ссылка на раздел и текущее название;
3. `<div class="operation-number">` и `<h1>` — номер и название;
4. блок «Необходимая документация» — разделы проекта (`АР, ЭОМ, КЖ…`) и
   ссылки на техкарты:
   ```html
   <a href="../../assets/docs/5.11_монтаж РК внутри панели стены.pdf" class="pdf-link">
       ... Название техкарты
   </a>
   ```
   Класс `pdf-link` обязателен — по нему работает просмотрщик PDF;
5. кнопку «Ознакомлен» — `data-op-id="X.Y.Z"` и `data-op-version="N"`
   (N = `version` из реестра, см. § 4);
6. навигацию «Предыдущая / Следующая» — соседние операции подраздела.

### Шаг 4. Реестр операций

`public/js/kb.js`, массив `KB_OPERATIONS` — вставить запись в нужный подраздел
(порядок строк = порядок вывода):

```js
{ id: '3.4.4',  section: 'module', title: 'Монтаж электроточек',
version: 1, status: 'draft',   url: 'pages/operations/3.4.4.html' },
```

Поля: `id` (`X.Y.Z`), `section` (`preparation` / `panels` / `module` /
`options` / `installation` / `service` / `standards`), `title`, `version`,
`status` (`draft` | `ready`), `url` (всегда `pages/operations/<id>.html`).

### Шаг 5. Ссылка в списке подраздела

Открыть страницу раздела (`public/pages/panels.html`, `module.html`,
`standards.html` …), найти `.accordion-section[data-section="X.Y"]` и добавить
строку в `<ul class="operations-list">`:

```html
<li><a href="operations/3.4.4.html">3.4.4 — Монтаж электроточек</a></li>
```

Список — обычный HTML, автоматической генерации из реестра нет, поэтому
пункт 5 существует отдельно от пункта 4.

### Шаг 6. Пересборка поискового индекса

```bash
npm run build-index
```

Скрипт `server/scripts/build-search-index.js` читает реестр и HTML-файлы,
пропускает `draft` и перезаписывает `public/js/search-index.json`.
Без этого шага операция существует, но не находится поиском.

### Шаг 7. Проверка

```bash
npm run audit
```

Скрипт `scripts/kb-audit.js` сверяет реестр, страницы, списки разделов и
индекс. Ошибки (код возврата 1) — то, что увидит пользователь: готовая
операция без страницы, расхождение `data-op-id`/`data-op-version`, отсутствие
ссылки в списке, битая ссылка на PDF, устаревший индекс. Предупреждения —
то, что скрыто от глаз: черновики без страниц, ненайденные фото.

## 4. Версии и кнопка «Ознакомлен»

`version` в реестре и `data-op-version` в HTML — это одно и то же число,
записанное в двух местах. Отметка «Ознакомлен» привязана к паре
`(id операции, версия)`.

**Правило: любое смысловое изменение содержания — это `version + 1` в обоих
местах.** Тогда у сотрудников отметка сбрасывается, и они обязаны перечитать
операцию. Если версию не поднять, люди останутся «ознакомленными» с текстом,
которого уже нет.

Правка опечатки в верстке, не меняющая смысла, версию не требует.

## 5. Статусы

| Статус | Что видит пользователь |
|--------|------------------------|
| `draft` | Черновик. Скрыт из поиска. В списке подраздела скрыт от всех, кроме администратора (ему показывается с меткой «Черновик») |
| `ready` | Полноценная операция: видна по правам раздела, попадает в поисковый индекс |

Перевод в `ready` — это два действия: `status: 'ready'` в реестре **и**
наличие страницы `X.Y.Z.html`. Запись в списке подраздела нужна в любом
случае — иначе операция недостижима навигацией.

## 6. Типичные ошибки

Собрано по аудиту текущего состояния базы.

1. **Забыли `npm run build-index`.** Поиск работает по снимку, а не по
   реестру: в индексе, который лежал в `main`, было 21 документ по старой
   схеме идентификаторов, и ни одной актуальной операции.
2. **Скопировали страницу и не заменили пути к фото.** Блок молча скрывается.
   В базе на момент аудита: 64 ссылки на несуществующие файлы и 30 ссылок в
   папку другой операции (2.1.6 → 2.1.5, 2.1.7 → 2.1.6 и так далее).
3. **`data-op-id` не совпадает с `id`.** Отметки ознакомления пишутся не в ту
   операцию. Аудит сверяет это автоматически.
4. **Черновик добавлен в список раздела, а страницы нет.** У администратора
   ссылка ведёт в 404 (61 такой черновик). Либо создайте страницу-заглушку,
   либо не добавляйте пункт в список до готовности.
5. **Не подняли версию после правки содержания.** Сотрудники не перечитают
   операцию.

## 7. Git-процесс

Работа идёт через ветку и Pull Request: `main` защищён от случайных правок
тем, что **merge в `main` автоматически деплоит сайт на VPS**
(`.github/workflows/deploy.yml`: `git pull` → `npm install` → `pm2 restart`).
То есть `main` — это продакшен, а не «ещё не готово».

```bash
git checkout -b feat/operation-3.4.4
# … правки …
npm run build-index && npm run audit
git add -A && git commit -m "создана операция 3.4.4, переведена в статус ready"
git push -u origin feat/operation-3.4.4
```

После merge в `main` деплой запускается сам, отдельного шага «выложить» нет.

## 8. Локальный просмотр

Страницы защищены проверкой прав (`access-guard.js` запрашивает `/api/me`),
поэтому открыть `public/index.html` двойным щелчком и ходить по разделам не
получится — без сервера будет редирект на страницу входа. Для просмотра нужен
запущенный бэкенд:

```bash
cd server
npm install
KB_JWT_SECRET=$(openssl rand -hex 32) KB_DB_PATH=./kb.sqlite \
  KB_ADMIN_PASS='пароль-министрадмина8' node init-db.js
KB_JWT_SECRET=<тот же секрет> KB_DB_PATH=./kb.sqlite node app.js
# http://127.0.0.1:3000
```

Демо-логины `admin/admin123`, `builder/build456`, `engineer/eng789` из
`README.md` больше не работают: `public/js/users.js` — заглушка, пользователи
хранятся в SQLite и создаются командой `init-db.js` (демо-аккаунты —
`KB_DEMO=1`).

**Известная проблема.** Каталог `public/js/pdfjs/` в репозитории отсутствует,
хотя `pdf-viewer.js` его импортирует. Модальное окно просмотра техкарт не
открывается, ссылка на PDF срабатывает как обычная и открывает файл в новой
вкладке. Сами техкарты при этом доступны.
